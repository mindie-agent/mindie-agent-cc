# MindIE Agent (Unified Entry)

Users interact with MindIE Agent through a single `/mindie-agent` entry (while `remote-dev` MCP tools trigger automatically by default when remote servers or NPU containers are involved):

1. **Domain Knowledge (`L1–L4`), Multi-Domain Routing, Three-Valued `conditions` & Remote NPU Execution**:
   - When the user asks an Ascend or `vLLM-Ascend` engineering question, use the native knowledge tools (`knowledge_query`, `knowledge_explain`, `knowledge_feedback`, `knowledge_distill`) and remote execution tools (`mindie-remote-dev`) directly.
   - **Graded Knowledge, Multi-Domain Routing, Reference Identity & `knowledge_distill`**: `knowledge_query` accepts `query`, optional `domain` (selecting the default domain or a registered `domain_configs` Engine/Feed such as `"vllm-ascend"` or `"operators"`), `limit` (1–20), `conditions`, `continuation`, `domain_path`, `token_budget` (1–16000), and `include_unknown`. For graded units, `results[]` return `id`, `ref` (`mindie://<domain>/units/<id>@<integer revision>`), `unit_ref` (without revision), and `feedback_ref` (equal to `ref` for graded units); pass query's readable `ref` or `unit_ref` to `knowledge_explain(ref)` to read `graded_unit` (which also returns `feedback_ref`, distinct from legacy task/block navigation) and copy the exact `feedback_ref` to `knowledge_feedback` (for graded units `ref` and `feedback_ref` share the same revision-bound URI value, whereas legacy material keeps `ref` and `feedback_ref` distinct; never pass a bare `id`; both `knowledge_explain` and `knowledge_feedback` route by the `mindie://<domain>/...` URI authority). Use `knowledge_distill(inputs, task_state, domain=...)` at `task_state="verified_milestone"` or `"completed"` on caller-selected, already-authorized evidence (`completed` or `verified_milestone` with `observed` or fault/environment/build evidence [`compile_failed` / `infra_failed` / `measurement_invalid`] is allowed and can yield `single_observation` or `hypothesis` without elevating unverified faults to `hardware_spec` or `reproduced_empirical`, while `reproduced_empirical` requires repeated `verified` evidence and `L4` requires a valid ablation receipt); only `task_state="in_flight"` (or all-`in_flight` / empty inputs) is a zero-call no-op. Graded query options, multi-domain routing, and `knowledge_distill` require the paired `mindie-knowledge 0.13.0` runtime. Graded Git publication (`mindie-publication-contract/2`), independent Feed sync, and revision-bound unit feedback use that runtime; check the selected feed revision and installed runtime identity separately when diagnosing a mismatch.
   - **P0–P3 Progressive Context & Experience Flywheel**: Load knowledge in two bounded steps instead of dumping bodies. First call `knowledge_query` and read `cards` (navigation: title, purpose, applicability, missing conditions, body cost, ref) plus deduplicated `foundation_cards` (shared `L1` premises); set `include_archived=true` only when investigating archived/superseded conclusions. Then call `knowledge_explain(refs=[...], conditions={...}, known_refs=[...], token_budget=...)` for the selected closure: shared ancestors appear once in `requires`, full bodies appear untruncated in `units`, `known_refs` lists only exact `id@revision` units still fully visible, and `unresolved` explains `condition_unknown` / `condition_mismatch` / `budget_excluded` / `removed_or_superseded` / `not_found` rather than dropping required steps. A single `ref` call keeps its legacy task/block navigation. At a verified milestone, close the experience loop with `knowledge_distill(inputs, task_state, related_refs=[...])` so existing units are compared as a delta before writing, or pass a foreground `mindie-distill-decision/1` `proposal` for deterministic validation and application with `model_calls=0`. Record usage as the 4-stage `knowledge_feedback(ref, event_type="discovered"|"loaded"|"applied"|"evaluated", run_id=..., step_id=..., outcome="supported"|"refuted"|"inconclusive")`; the legacy `rating="up"|"down"` vote remains valid but proves neither adoption nor effectiveness. Judge exploration results on three independent axes—`Performance`, `Correctness/Invariants`, and `Diagnostic Information Gain`—so a small valid win below target is not a refuted mechanism, a correctness failure is not a performance result, and a valuable diagnostic conclusion still counts.
   - **Three-Valued `conditions` Rule (`matched` | `mismatched` | `condition_unknown`)**: Units separate functional `tier` (`L1–L4`) from `evidence_strength` (`hardware_spec`, `reproduced_empirical`, `single_observation`, `hypothesis`) and evaluate their declared condition keys. `condition_unknown` occurs when either the unit's declared `required` premise or the caller's `observed` fact is `"unknown"`, missing/not supplied, or has an incomparable format, and `unknown == unknown` never matches (an absent requirement or `"any"` is unconstrained `matched`, and historical `required: "unknown"` is never backfilled by later machine versions)—never treat `condition_unknown` as a match; verify whichever fact is missing/unknown (e.g., source `repository`/`revision` for an `L2` source SOP, or runtime environment for an NPU rule).
   - **Physical NPU Timing Mutual Exclusion & Profiler Discipline**: CPU pre-compilation (`npu_count=0`) may run in parallel across per-slot caches, whereas performance timing, Gate 3/4 checks, and `mindie_profiler` runs on the same physical NPU (or same A3 dual-Die package) require an exclusive `coordinator` lease. `mindie_profiler` accepts explicit unlabeled `--time-window START:END`, labeled `--step-window STEP=START:END`, or `--full-range` (never inferring steps from kernel rows), uses explicit scene/clock annotations (`uncertain` / `clock_domain_unknown` otherwise), keeps single-kernel roofline bounds separate from unverified external `msmodeling` predictions, and never infers thermal throttling from a static `85°C` threshold.
2. **Status & Hook Context**: When `/mindie-agent` is invoked explicitly for status or setup, present the MindIE status from the `UserPromptExpansion` hook context. Never invent a session ID, repository, account, or project scope.
3. **Automatic Experience Loop, `Stop` Boundary & Long-Horizon Continuation Ledger**:
   - Once community contribution is configured and enabled for the project scope, eligible native `Stop` events are captured, redacted, and packaged automatically in the background—users never need to ask to save experience at the end of a session.
   - **Host `Stop` != Long-Horizon Task Completion**: A single-turn `Stop` hook only hands off that turn's completed public transcript; it does not mean a multi-turn or multi-day engineering task is finished (`task_state="in_flight"` triggers a zero-call no-op in `knowledge_distill`).
   - **Launch-Time `in_flight_runs` Registration & Recovery-First-Query**: Immediately when `coordinator` or `remote-dev` launches a run or job, atomically update `PROGRESS.md` to register its `run_id` (`run_id == execution_id`, never replaced) or `job_id`, `slot_id`, endpoint, and `Run Manifest` path under `in_flight_runs` before polling or ending the turn. On resume or after compaction, query `in_flight_runs` first and never resubmit a duplicate command. Keep `Run Manifest` execution facts separate from condition-scoped hypothesis judgments in `experiment-ledger.jsonl`, never overwrite a succeeded remote run due to a local receipt/ledger error, and treat `candidate_for_sequential_pruning` with `pruned_combination_verified=false` as **RETAIN**.
4. **Unified Contribution & Fault-Reporting Switch**: Community knowledge sharing and sanitized product fault reporting share a single persistent choice in `<adapter-config-directory>/mindie-consent.json`. When the native Hook returns `reporting.run_outside_hook=true`, execute its `reporting.command_line` immediately outside the Hook in the same setup flow (using a 90-second outer timeout) without asking for another confirmation or leaving the command for the user. Reuse a valid saved choice without another prompt. Only when the entry returns `needs_choice` for legacy knowledge-only `contribute`, resolve it once through `/mindie-agent`; never split knowledge/reporting approvals or ask per task. Keep saved `disabled`, `read-only` and `later` choices without prompting. Keep three states strictly separate: (1) local consent configuration saved, (2) background reporter worker running (`reporting.status == "running"`), and (3) external GitHub Issue/PR created. Report `degraded`, authentication errors, timeouts, and `needs_choice` directly, and never retry an uncertain external write.

Resolve the installation's base adapter configuration first (`base_config` for a runtime binding); its parent contains `mindie-consent.json`. Use the existing entry to change the choice, never a guessed profile path.

## Graded Execution Loop (`L1` → `L2` → `L3` → `L4`)

Graded guidance follows the `0.0.3` single-line `ID@revision` contract published from the moving `main` branch: cite `mindie://<domain>/units/<id>@<integer revision>` and use the observed integer `revision` as identity; never require or derive a closure, content, or contract digest.

- **`L1` + `L2` Foundation Baseline**: Querying with observed `conditions` mounts `_common` `L1` hardware/runtime axioms and measurement gates (`inherited_rules` or `route: 'foundation_baseline'`) alongside `L2` bottleneck/triage SOPs. Never invent an unobserved premise; an unproven condition stays `condition_unknown` rather than becoming baseline.
- **`L3` Hermes Mode (Heuristic Convergence & Skill Self-Evolution)**: Execute `L3` staged convergence workflows (`category: workflow`), record structured probes, and call `knowledge_distill` at verified milestones (`task_state: 'verified' | 'completed'`; the runtime token for the verified milestone is `verified_milestone`) plus `knowledge_feedback` for the observed `unit_id` + integer `revision` (through the exact revision-bound `feedback_ref`) to close the P3 reuse flywheel.
- **`L4` RSI Mode (Recursive Self-Improvement De-biased Exploration)**: When `L3` routine workflows stall after 2 attempts, escalate to `L4` RSI mode—strip `L3` routine workflow bias, keep only `Goal + L1 foundation + L2 bottleneck data + L4 mutators + experiment-ledger.jsonl conditional_avoid`, run parallel CPU compile (`npu_count=0`) + serial exclusive NPU timing (`devices=[0]`), enforce Gate 1–4 (`OracleFreezer`, `MeasurementGuard`, `AblationGate`, `Distill/Refute`), append `supported`/`refuted` (`conditional_avoid`) to `experiment-ledger.jsonl`, and update `PROGRESS.md`.
