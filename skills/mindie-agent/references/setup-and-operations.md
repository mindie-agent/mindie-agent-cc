# Setup, Contribution Configuration & Operations (Claude Code)

Load this reference **only** when the user is performing first-time setup, configuring or changing community experience contribution, configuring fault reporting, or troubleshooting capture status.

## 1. Community Experience Contribution Setup

- **Default Automatic Loop After Opt-In**: Once contribution is configured and enabled for the approved project scope, eligible native `Stop` events automatically capture the current task's public transcript, run deterministic local redaction + Gitleaks scanning, and prepare a knowledge PR in the background. Users never need to ask to save experience at the end of each task.
- **Completing Incomplete Configuration & On-Demand Knowledge Repo Fork**:
  - Installation requires no Star or Fork; starring a project is optional user support. Only after the user explicitly enables contribution (`contribute`) for a target public knowledge repository `owner/repo` (such as `mindie-agent/knowledge-vllm-ascend`), create its fork as needed through the authenticated `gh` channel:
    ```sh
    gh repo fork owner/repo --clone=false --remote=false
    ```
  - If contribution configuration is incomplete, reuse any already-approved values, ask only for the missing destination and scope, and bind `--fork USER/repo` so contribution branches push to the user's personal Fork:
    ```text
    /mindie-agent contribute --repository owner/repo --account USER --fork USER/repo --project-root /absolute/path --visibility public
    ```
  - Configuration and actual processing receipts are distinct facts: never report a PR as created or merged unless confirmed by a receipt.
- **Persistence & Disablement**:
  - There is no automatic opt-in ("no automatic yes").
  - A saved choice persists across sessions, forks, restarts, upgrades, and failures—it is never re-asked, and failure counts never revoke it.
  - Explicit disablement and legacy declined settings stay disabled until the user explicitly changes them; they are not alternative product modes or successful acceptance.

## 2. First-Use Onboarding & Optional Workspace Setup

During installation or first-use setup:
1. Present [用户须知](user-notice.md) (which explains visible-message sharing, redaction limits, model-provider processing, and public Git history).
2. Follow [optional workspace setup](workspace-setup.md): recommend the multi-worktree workspace (`vllm` + `vllm-ascend`), ask whether and where to create it, and after creation ask whether to initialize it. Reuse prior answers and offer this only during setup rather than ordinary task execution.
3. **Unified Contribution & Fault-Reporting Switch**:
   - Resolve the installation's base adapter configuration (`base_config` in a runtime binding); `base_config.parent / "mindie-consent.json"` is the sole choice authority. Use the native entry, not direct file edits.
   - Community knowledge sharing and automatic tool fault reporting share a single persistent choice in `<adapter-config-directory>/mindie-consent.json`, authorizing both scoped knowledge PRs and sanitized product fault Issues.
   - Reuse a valid saved choice. Only when the entry returns `needs_choice` for a legacy knowledge-only `contribute` choice, resolve it once through `/mindie-agent` using the user's explicit choice. A contribution request already made in the current setup flow is that choice, not a reason to ask again. Saved `disabled`, `read-only` and `later` choices stay unchanged without prompting. Startup never grants missing permission, and ordinary tasks never repeat this choice.
   - When the native Hook returns `reporting.run_outside_hook=true`, execute `reporting.command_line` immediately outside the Hook in the same setup flow (using a 90-second outer timeout) as part of the user's contribution request—do not ask for another confirmation or leave the command for the user.
   - Keep three states strictly separate: (1) local consent configuration written, (2) background reporter worker running (`reporting.status == "running"`), and (3) external GitHub Issue/PR created. Report `degraded`, authentication errors, timeouts, and `needs_choice` directly, and never retry an uncertain external write.

## 3. Error Handling & Background Worker Rules

- Report missing configuration, an out-of-scope task, or a component failure directly to the caller when relevant.
- Ordinary tasks have no `activate` / `lease` / `recover` step. Do not require a `deactivate` / `reactivate` cycle to recover from a component failure.
- **Multi-Domain Route Registration, Target-Domain Activation & Bare `/mindie-agent deactivate`**:
  - Registering an additional domain Engine/Feed in an existing base adapter config uses `python -m mindie_knowledge.loop.domain_routes register --adapter-config <path> --domain <domain> --engine-config <path>`, which updates `domain_configs` (preserving `default_domain`) and **never** creates or widens `consent`.
  - Ordinary reads (`knowledge_query(domain=...)`, `knowledge_explain(ref="mindie://<domain>/...")`) do not widen authorization. Distilling or contributing to a registered target `domain` requires that target domain's own existing `consent` and `project_root` scope plus explicit target activation via `/mindie-agent --domain <domain>` (which binds only the target domain's `Admission` lease without replacing the default task binding).
  - Explicit `/mindie-agent deactivate` (taking no arguments) revokes **only the current `session_id`** across the default domain and all registered `domain_configs` (never revoking other sessions) and remains in force for that task. If any registered domain fails or times out during revocation, `status="partial"` (`partial=True`) is returned while preserving `changed` and per-domain outcomes (`domains[]`), keeping partial failure and already-revoked side effects distinct.
- The background worker reports processing failures separately from captured material and preserves billed or uncertain model outcomes; **never** replay a model invocation to recover a missing receipt.
- A single-turn native `Stop` event only hands off the completed turn's public transcript slice; it does **not** mean a multi-turn or long-horizon engineering task has concluded. In-flight or unverified turns are not promoted into `reproduced_empirical` knowledge units, and local receipt/organizer accounting errors never overwrite a succeeded remote execution result.

## 4. Graded Knowledge (`L1–L4`), `knowledge_distill`, Long-Horizon Continuation Ledger & Profiler Discipline

- **Graded Execution Loop (`L1` → `L2` → `L3` → `L4`) & the `0.0.3` Single-Line `ID@revision` Contract**:
  - **Reference Identity**: Public graded references are the single-line `ID@revision` form (`mindie://<domain>/units/<id>@<integer revision>`) published from the moving `main` branch. Record `unit_id` and the integer `revision` when citing knowledge; never ask callers to compute or verify closure, content, source, or contract digests, and never depend on a versioned publication path.
  - **`L1` + `L2` Foundation Baseline**: Querying with observed `conditions` mounts `_common` `L1` hardware/runtime axioms and measurement gates (`inherited_rules`, or `route: 'foundation_baseline'` when the `L1` unit is mounted directly) alongside `L2` bottleneck/triage SOPs. The baseline is condition-bound: a missing/unknown observed fact or a mismatched `_common` parent excludes the rule instead of widening it.
  - **`L3` Hermes Mode (Heuristic Convergence & Skill Self-Evolution)**: Execute `L3` staged convergence workflows (`category: workflow`) as the routine path, record structured probes (goal, observed `conditions`, commands, run/ledger receipts, and outcome), and call `knowledge_distill` at verified milestones (`task_state: 'verified' | 'completed'`; the runtime token for the verified milestone is `verified_milestone`) with caller-selected, already-authorized evidence. Then call `knowledge_feedback` for the observed `unit_id` + integer `revision` (pass its exact revision-bound `feedback_ref`) to close the P3 reuse flywheel. `task_state="in_flight"` remains a zero-call no-op, and a single `observed` result must not become `reproduced_empirical`.
  - **`L4` RSI Mode (Recursive Self-Improvement De-biased Exploration)**: When `L3` routine workflows stall after 2 attempts, escalate to `L4` RSI mode—strip `L3` routine workflow bias, keep only `Goal + L1 foundation + L2 bottleneck data + L4 mutators + experiment-ledger.jsonl conditional_avoid`, run parallel CPU compile (`npu_count=0`) + serial exclusive NPU timing (`devices=[0]`), enforce Gate 1–4 (`OracleFreezer`, `MeasurementGuard`, `AblationGate`, `Distill/Refute`), append `supported`/`refuted` (`conditional_avoid`) to `experiment-ledger.jsonl`, and update `PROGRESS.md`.
- **Graded `knowledge_query`, Multi-Domain Routing, Reference Identity & `knowledge_explain` / `knowledge_feedback` Contract**:
  - `knowledge_query` accepts `query`, optional `domain` (explicitly selecting the default domain or a registered `domain_configs` Engine/Feed such as `"vllm-ascend"` or `"operators"`; cross-domain references use existing `source_locator` / `evidence_refs` links rather than automatic federated retrieval), `limit` (`1..20`), `conditions`, `continuation`, `domain_path`, `token_budget` (`1..16000`, default `800`), and `include_unknown` (default `false`).
  - When a graded corpus is installed (`retrieval: "graded-bm25"`, `page: "graded_units"`), `results[]` items return `id` (`unit-...`), `ref = "mindie://<domain>/units/<id>@<integer revision>"` (bound to the observed revision), `unit_ref = "mindie://<domain>/units/<id>"` (without revision), `feedback_ref = ref` (the same revision-bound URI for graded units), `revision`, `match_status` (`matched` | `mismatched` | `condition_unknown`), `missing_conditions`, `tier`, `category`, `evidence_strength`, `domain_path`, `conditions`, `provenance`, `excerpt`, `inherited_rules` (each with its own `ref`), and `inheritance_excluded`.
  - Pass query's readable `ref` (`mindie://<domain>/units/<id>@<integer revision>`) or `unit_ref` to `knowledge_explain(ref)`, and copy the exact `feedback_ref` to `knowledge_feedback` (**never pass a bare `id`**; for graded units `ref` and `feedback_ref` share the same revision-bound URI value, whereas legacy material keeps task/block `ref` and `feedback_ref` distinct without mixing their roles). Both `knowledge_explain` and `knowledge_feedback` route by the URI authority domain (`mindie://<domain>/...`), and `knowledge_feedback` requires the exact returned revision URI (`feedback_ref` / `/units/<id>@<integer revision>` for graded units, or legacy `feedback_ref` for legacy material). For a graded unit, `knowledge_explain` returns `kind: "graded_unit"` (`ref`, `unit_ref`, `feedback_ref`, `id`, `revision`, `frontmatter`, `content`, `inherits_from_closure`), **not** legacy `first_block_ref` / `previous_block_ref` / `next_block_ref` navigation (which applies only to legacy task/block references). Record `id` (`unit_id`) and `revision` when citing knowledge; do not ask callers to compute or verify content, source, contract, or closure digests, and treat any informational digest fields as metadata rather than reference identity.
- **Three-Valued `conditions` Evaluation (`matched` | `mismatched` | `condition_unknown`)**:
  - Units separate functional `tier` (`L1` axioms & probes, `L2` SOPs, `L3` convergence workflows, `L4` exploration mutators) from `evidence_strength` (`hardware_spec` | `reproduced_empirical` | `single_observation` | `hypothesis`).
  - Query evaluates the exact condition keys declared in each unit's `conditions` mapping (such as `soc`, `cann`, `driver`, `framework`, `repository`, `revision`, `workload_scope`, `dtype`, `input_shape`, or `workload_case_sha256`; never assume a hardcoded legacy condition-key list). Inherited `_common/` rules evaluate their own declared `conditions` independently without widening scope.
  - `condition_unknown` occurs when either a declared `required` premise on the unit or the caller's `observed` fact is `"unknown"`, missing/not supplied, or has an incomparable format, and `unknown == unknown` never matches (an absent requirement or `"any"` is unconstrained `matched`, and historical `required: "unknown"` is never backfilled by later machine versions). **Never** treat `condition_unknown` as `matched`; verify whichever fact is missing or unknown first (e.g., source `repository`/`revision` for an `L2` source SOP, or runtime environment for an NPU rule).
- **Explicit Selected-Evidence Distillation (`knowledge_distill`) & Paired-Runtime Boundary**:
  - `knowledge_distill(inputs, task_state, domain=...)` distills caller-selected, already-authorized evidence (`inputs` items with `kind` in `experiment_ledger | run_manifest | authorized_transcript | ecosystem_repo | hardware_spec | ablation_receipt`, `outcome` in `observed | verified | compile_failed | infra_failed | measurement_invalid | in_flight`, `source_locator`, `content`, `evidence_refs`, optional `repetitions >= 1`) under the active task capture lease (`SummaryLedger`) for the default or activated target `domain`.
  - Use `task_state="verified_milestone"` or `"completed"`: `observed` as well as fault/environment/build evidence (`compile_failed`, `infra_failed`, `measurement_invalid`) can be distilled into `single_observation` or `hypothesis` (preserving its true `evidence_strength` without elevating unverified fault/build evidence to `hardware_spec` or `reproduced_empirical`; `hardware_spec` specifically requires a `hardware_spec` source, `reproduced_empirical` specifically requires `outcome == "verified"` with `repetitions >= 2`, and `L4` specifically requires a verified `mindie-bench-ablation/1` receipt). Only `task_state="in_flight"` (or all-`in_flight` / empty inputs) is a deterministic zero-call `noop`, and an ordinary host `Stop` event is **not** task completion. Local receipt/application failures preserve a completed native model result (`operation_status="local_receipt_failed"` or `"local_application_failed"`, `local_error`) without replaying the paid call.
  - **Release Boundary**: `knowledge_distill`, multi-domain routing, and graded `knowledge_query` options (`domain_path`, `token_budget`, `include_unknown`) depend on the paired `mindie-knowledge 0.13.0` runtime. It supports graded Git publication (`mindie-publication-contract/2`), independent Feed sync, and revision-bound unit feedback (`feedback_ref` / `/units/<id>@<integer revision>`). The selected feed revision and installed runtime identity are separate facts; use their own receipts to verify them.
- **Long-Horizon Continuation Ledger (`PROGRESS.md` + `experiment-ledger.jsonl`, No Second State Machine)**:
  - **Launch-Time `in_flight_runs` Registration & Atomic `PROGRESS.md` Replacement**: `coordinator` assigns `run_id` (`run_id == execution_id`) at submission (`client.run`), and a submitted `run_id` is never replaced. Immediately upon launching any run/job (before waiting or ending the turn), atomically update `PROGRESS.md` (`os.replace`) to record `{run_id, job_id, slot_id, host_endpoint, manifest_path, started_at}` under `in_flight_runs`, alongside the task goal, current workspace `git_commit`/`diff_digest`, verified baseline `run_id`, best verified candidate `run_id`, key historical `conditional_avoid` refs, and the next minimal experiment.
  - **Recovery-First-Query Rule**: After any context compaction, interruption, or session resume, read `PROGRESS.md` `in_flight_runs` first and query the original `run_id` / `job_id` (`TaskClient.observe(run_id=...)` / `remote_job_status`) before taking any action—**never** resubmit a command while its in-flight `run_id` is active or unresolved.
  - **Single-Writer `experiment-ledger.jsonl` & Sequential Pruning Consumer Rule**: Append one JSON record per experiment linking `task_id`, `exp_id`, `run_ids`, `hypothesis`, `factors`, `factor_roles` (`performance` | `correctness_required` | `dependency` | `inseparable_group`), `unit_refs` (`unit_id` + `revision`), `receipt_refs`, `run_status` (`passed` / `failed` / `inconclusive` / `cancelled`), `judgment` (`supported` / `refuted` / `inconclusive`), `scope_conditions`, and optional `conditional_avoid` / `supersedes_exp_id`. Compile/SSH/measurement faults are `inconclusive` (not `refuted`). In Contract C4 (`AblationReceipt`), LOO `delta <= tolerance` only sets `disposition: "candidate_for_sequential_pruning"`; consumers **must** treat `disposition == "candidate_for_sequential_pruning"` with `pruned_combination_verified == false` as **RETAIN**, and `L4` distillation requires a baseline-bound verified final-combination ablation receipt (`final_combination` with `final_combination_verified == true` and `correctness_verified & performance_verified`, even when no pruning occurred and `pruned_combination_verified == false`; or legacy `pruned_combination` with `pruned_combination_verified == true` and non-empty passing `pruning_verifications` ending in that final combination).
- **Parallel Pre-Compilation, Exclusive Physical NPU Timing & Profiler Discipline**:
  - Multi-candidate ideation and `npu_count=0` CPU pre-compilation (using per-slot `MINDIE_SLOT_ID` cache paths) may run in parallel, but **performance timing, Gate 3/4 verification, and `mindie_profiler` collection on the same physical NPU (or same A3 dual-Die package) must run under an exclusive `coordinator` lease**.
  - **Explicit Unlabeled or Labeled Windows (`segment.py`) & Scene/Clock Annotations**: `python -m mindie_profiler` supports **explicit unlabeled time windows** (`--time-window START:END` / `--window START:END`), **explicit labeled step windows** (`--step-window STEP=START:END` / `--step STEP=START:END` / `--steps-file`), and explicit `--full-range` (in `--unit us|ns|ms`). Not every analysis requires step labels, and `segment.py` **never** auto-infers real step identity from kernel rows, timestamps, or CSV headers. Scene metadata (`--mode`, `--framework`, `--phase`, `--tp`, `--dp`, `--graph-mode`, `--clock-domain`, `--input-signature`) uses explicit caller annotations and reports `uncertain` otherwise (`scene_detector.py`). Multi-rank DBs without `--clock-domain` emit `measurement_limitation: "clock_domain_unknown"`, and `compare.py` refuses cross-run timing comparison unless `clock_domain` matches.
  - **Non-Additive Time Views, Three-Time Separation & Unverified `msmodeling` Provider**: `busy_union` and `kernel_sum` are non-additive (`host_gap = wall - busy_union`, `exposed_comm = comm_union - noncomm_union`), and `slowest_rank` is chosen by wall `p50` across 7 semantic blocks. `theoretical_model.py` separates `ideal_hardware_lower_bound_ms` (local `roofline-max-v1` single-kernel bound, not a whole-network bound), `model_predicted_ms` (only from an injected validated external provider with real version, matching protocol, matching `input_signature`, and non-empty evidence; otherwise `None` with `unmodeled_reason`), and `measured_device_ms`; `probe_msmodeling_adapter` reports install state only and never imports/executes `msmodeling` (`verified=False`). Never infer thermal throttling from `>= 85°C` (`used_as_throttling_proof=False`); rely on explicit hardware throttle signal bits or record `measurement_limitations`.
